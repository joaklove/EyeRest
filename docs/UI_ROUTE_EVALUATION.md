# EyeRest UI 路线评估：能否 1:1 复刻「方案三」展示板

- 评估日期：2026-09-11（同日修订：展示板原图落库、取色实测、路线正式决议）
- 代码基线：V0.6.2（c0bbf68）
- 被测对象：用户提供的「方案三：轻奢艺术 · 温暖治愈」展示板 + 一份锁定该方案的实现 Prompt
- 视觉基准：`docs/design/reference/方案三-轻奢艺术-温暖治愈.jpg`（**唯一 Source of Truth**）
- **文档状态：已确认为 EyeRest 后续 UI 路线的决策依据。正式决议见 §7，取色实测见 §12。**

---

## 0. 结论摘要

| 问题 | 答案 |
|---|---|
| 现在的 Qt Widgets 精修能做到 1:1 吗 | **不能**，整屏观感上限约 80% |
| 换控件级（自绘 toggle/输入框/投影）能到 1:1 吗 | **不能**，上限约 85%，只解决"控件形态"一维 |
| 选 Web 能做到 1:1 吗 | **仍不能**，上限约 95%。Web 消除的是"引擎能力天花板"，但消除不了"目标不是规格书"这一层 |
| 那 Web 值不值得做 | 取决于一个前置尖刺：**透明 + 置顶 + 不抢焦点的提示条在 WebEngine 上能否稳定工作**。能，才值得投入；不能，整条路线否决 |
| 性价比拐点在哪 | **Qt Quick（QML）**：+20~40 MB 拿到 92%；Web 要 +200~250 MB 才多拿 3 个百分点 |

**一句话**：现在的差距里，只有约 25% 是"引擎不够用"，约 60% 是"资产质量"，约 15% 是"活数据 vs 静帧"。换引擎只能吃掉那 25%。

## 1. 先评估这份方案本身（不是方案不好，是它不完整）

### 1.1 它对现状的判断是错的（会导致大量重复劳动）

方案里说"方案三不是 Calm Dark，方案三 = 轻奢艺术·温暖治愈"，并据此要求按展示板实现。**这条纠正的正确性没问题，但它纠正的是一个已经不存在的问题**——V0.6 起项目就一直按暖色方案走（`tokens.py` 里 `PRIMARY = #4CCAB8`、`BG_CANVAS = #FBF5EF`），从未实现过 Calm Dark。

更要紧的是，方案中列为"要做的"条款里，**至少 5 条已经完成**：

| 方案条款 | 实际状态 |
|---|---|
| Settings 四个节奏 2×2 卡片网格 | ✅ V0.6.1 已完成 |
| 数字输入禁用 QSpinBox 的 +/- 箭头 | ✅ V0.5.1 已完成（`ButtonSymbols.NoButtons`） |
| 保存反馈不弹 QMessageBox、约 1.5s 自动消失 | ✅ 已完成 |
| PositionEditor 保留 VisualCuePreview 架构、不 reparent | ✅ V0.6 已完成（单顶层 + 独立子控件） |
| 插画资产化（眼睛/植物/小动物/节奏图标） | ✅ V0.6.2 已完成 18 个 SVG |
| 品牌字体 | ✅ V0.6.2 已嵌入站酷快乐体 |
| 五种声音方案 + 试听 + "不频繁打扰"原则 | ✅ 已完成 |
| **VisualCue 运行时皮肤暖色化** | ❌ **未做**（旧 emoji 皮肤仍在） |
| **Hero 植物背景 + 右上角四行节奏总览** | ❌ **未做**（当前 Hero 无 RhythmSummary 区块） |
| **Settings 分区改名为 视觉提醒/声音设置/系统设置** | ❌ 未做（当前为 视觉提醒/声音/系统/语言） |

**结论：这份 Prompt 的增量只有 3 项。** 直接交给 Codex 执行，它会重做大量已有功能，甚至可能退回已被验证错误的实现方式（例如重新尝试 reparent）。

### 1.2 它的色值来源是图上标注，而图上标注不可信

> **本节于 2026-09-11 二次修订。** 原版称"方案文本抄错了色值"（错）；一次修订称"错的是标注本身"（方向对，但**过度推广**）；二次修订基于四张色卡全量量化，结论收窄为：**只有主色的标注失真，其余三色标注是准的**。

| 用途 | 展示板自标注（= 方案文本） | 实测采样 v2 | 仓库 tokens（旧） | 判定 |
|---|---|---|---|---|
| 主色 | `#4CAF8A`（R76） | `#26AE89`（R38） | `#4CCAB8`（H171 S62 V79） | 🔴 需校准（已校准为 `#26AE89`） |
| 辅助色 | `#F8F5EF` | `#FBF4EC` | `#FBF5EF` | 🟢 一致 |
| 强调色 | `#FFD6A8` | `#FDD49B` | `#FFD9AB` | 🟢 一致 |
| 文字色 | `#2D3748` | `#373F4F` | `#2D3748` | 🟢 一致 |

三层事实：

1. **逐色判定，不要整体打折。** 用同一方法测四张色卡，辅助/强调/文字三色 ΔRGB 都落在 JPEG 噪声量级；只有主色偏差 R 通道 +38（标注偏淡，S57 vs 实画 S80）。"AI 标注不可信"在这一张图上**只对主色成立**。
2. **色相是本次最硬的结论。** 六路独立采样（色卡圆、实心按钮、标题胶囊、滑杆填充、全图最饱和 10%、色相直方图峰值簇）全部落在 **H 162.6–164.0**，收敛度极高，可直接采用。
3. **仓库旧 tokens 的偏差方向是"更青 + 更淡 + 更亮"**：`#4CCAB8` vs 实画 `#26AE89` → 青 7.7°、淡 15.8pt、亮 11pt。这正是"我们的绿像薄荷青、展示板的绿像植物绿"的量化原因。

**行动项（已完成）**：展示板原图已落库至 `docs/design/reference/方案三-轻奢艺术-温暖治愈.jpg`；完整取色报告见 `docs/design/README.md`，摘要见本文 §12。主色已按 `#26AE89` 全量替换。

### 1.3 它没有验收标准

方案的目标函数是"尽可能接近"。这是不可验收的——**没有终点的目标会让每一轮迭代都继续不满意**。必须换成逐区块判定（见第 6 节）。

### 1.4 一个被忽略的信息架构新增

方案的 Hero 要求右上角放一个白色半透明的**四行节奏总览**：

```
护眼节奏运行中
眨眼提醒   60秒 / 10秒
远眺提醒   20分钟 / 20秒
活动提醒   45分钟 / 3分钟
长休息     90分钟 / 5分钟
```

这是新增区块，需要接真实配置值，且要在 900px 宽、125% DPI、英文界面下处理换行。它不是"改颜色"，是"加功能"——属于 UI 层但会动布局。

## 2. 为什么 1:1 不可能：四层天花板

### 第 0 层｜目标本身不成立（占差距约 40%，最致命）

1. **那张图是多面板 moodboard，不是单屏规格。** 一张图里塞了首页、设置页、位置编辑器、声音面板、色卡标注、设计原则文字。右侧色卡区根本不是 UI 界面。"1:1 复刻整张图"在数学上不成立——它不描述任何一个 900×680 的屏幕。
2. **它是 AI 生成的。** 里面的文字字形是模型理想化的笔形，不对应任何真实字体；标注的色值如上文所述不可靠。换任何真字体、任何色值都只能"神似"。
3. **它只画最美状态。** 无滚动条、无禁用态、无 `--` 占位、无空数据、无长英文（英文界面文本长度约为中文 1.6 倍）、无 125% DPI。
4. **它有构图自由度，我们没有。** 展示板可以奢侈留白，因为它不需要装下 10+ 个设置项、真实状态文案、底部按钮栏。

### 第 1 层｜渲染引擎（Qt Widgets 的硬墙，有证据）

| 能力 | Qt Widgets 实况 |
|---|---|
| 多层柔光投影 | ❌ `QGraphicsDropShadowEffect` 一个 widget 只能挂**一个**，且无法与 opacity 叠加。要双层柔光必须包容器或自绘 |
| 背景模糊（backdrop-filter） | ❌ 完全没有。`QGraphicsBlurEffect` 只能模糊自身内容，不能模糊背后内容 |
| **CSS 表现力** | QSS 不是 CSS：支持 `qlineargradient`/`qradialgradient`，但**不支持 box-shadow、不支持多背景层、不支持 transform 动画、不支持 transition/easing** |
| 原生控件内饰 | ⚠️ QComboBox 的 popup 列表、QCheckBox 的勾、QSlider 把手只能改到"皮肤级"，Windows 原生 popup 是无圆角矩形 |
| 行距 / 字距 | ⚠️ QSS 无 `line-height`（须 QTextDocument 或手工 padding），无 `letter-spacing`（须 `QFont.setLetterSpacing`）。展示板一半的"松弛感"来自行距 |
| DPI 缩放 | ⚠️ 125% 下 QSS 里的 px 会被缩放，像素级对齐漂移 |

→ Qt Widgets 真实上限：骨架/配色/间距 **90%+**，控件形态 **85%**，光影材质 **40%**，整屏观感 **~80%**。

### 第 2 层｜资产质量（占差距约 60%，与引擎无关，是可解的）

- 当前 18 个 SVG 是**扁平色块 + 单层线性渐变**，没有体积光、没有柔和内部阴影、没有辉光、没有纸感纹理。
- 展示板的插画是有柔光与体积的角色插画。这不是控件问题，是**绘制质量代差**。
- 可解方案：① 用 ImageGen 生成柔光质感位图替换主插画（图标仍留矢量）；② 在手绘 SVG 里叠高斯模糊滤镜层 + 多层渐变。两者都能显著改善，但**仍然不会像素一致**。
- 字体：站酷快乐体已嵌入且效果已对上气质。但展示板字形是模型理想化的，任何真字体都只是"像"。

### 第 3 层｜内容是活的（不可消除，约 15%）

静帧 vs 活数据。产品要渲染 `--`、00:00、超长状态文案、禁用按钮、空统计、英文界面、滚动条。展示板里这些都不存在。

## 3. 三条路线量化对比

| 维度 | Qt Widgets 精修 | Qt Quick (QML) | Web (QtWebEngine) |
|---|---|---|---|
| 光影与材质 | 40% | 90% | 95% |
| 控件形态 | 85% | 95% | 95% |
| 排版与文本控制 | 60% | 85% | 98% |
| 字体 | 100%（已嵌入） | 100% | 100% |
| 插画 | 取决于资产 | 取决于资产 | 取决于资产 |
| **整屏观感可达** | **~80%** | **~92%** | **~95%** |
| 产物增量 | 0 | **+20~40 MB** | **+200~250 MB** |
| 内存增量 | 0 | ~+20 MB | ~+150 MB（多进程） |
| UI 层重写量 | 0（增量改，6055 行） | 6055 行全量改写 | 6055 行全量改写 + 前端工程 |
| 业务层（4441 行） | 零改动 | 零改动 | 零改动 |
| 测试影响 | 无 | UI 测试需重写，业务测试不动 | 同左 |
| 上手风险 | 低 | 中（QML 调试、打包需带 qml 目录） | 高 |

### 实测体积数据（本机 PySide6 6.11.1）

```
Qt6WebEngineCore.dll          195.3 MB   ← 不可裁剪的地板
resources/icudtl.dat           10.0 MB
resources/qtwebengine_resources.pak   2.3 MB
resources/qtwebengine_devtools_resources.debug.pak  75.8 MB   ← 可完全剔除
resources/qtwebengine_locales/  53 个 locale pak（保留 zh-CN + en-US 即可）

WebEngine 最小净增 ≈ 195 + 10 + 2.3 + ~3 ≈ 211 MB
dist 144 MB  →  Web 版约 355 MB（激进裁剪后）
```

### 为什么推荐 Qt Quick 作为拐点

本机已确认 **PySide6 6.11.1 Addons 全量安装**，以下模块可直接用、无需新依赖：

- `QtQuick/Effects`（**MultiEffect**：阴影、模糊、遮罩、着色，GPU 加速）
- `QtQuick/Shapes`（矢量路径绘制，带渐变）
- `QtQuick/Controls`（含 `FluentWinUI3` / `Basic` 风格，可完全自定义）
- QML 模块总体积仅 **30 MB**（`F:/Lib/site-packages/PySide6/qml`）

即：**+20~40 MB 换 92%**，而 Web 要 **+200~250 MB 换 95%**。多花的 200 MB 买的是那 3 个百分点和"排版自由"。

## 4. Web 路线具体方案（按要求给出）

### 4.1 宿主选型：三种，结论选 A

| | 方案 | 体积 | 问题 |
|---|---|---|---|
| **A** | **QtWebEngine（QWebEngineView）** | +211 MB | PySide6 自带，跨机渲染一致。**唯一不违反"零 C 盘写入"的选项** |
| B | WebView2（Edge Chromium，pywebview 或自建宿主） | ~0 | ⚠️ **直接冲突硬约束**：Win10 未预装时安装程序须写 `C:\Program Files (x86)\Microsoft\EdgeWebView\Application`；用户数据默认落 `%LOCALAPPDATA%`（C 盘）——后者可用 `WEBVIEW2_USER_DATA_FOLDER` 重定向到 G，前者不行。且版本随系统漂移，渲染不可控 |
| C | 本地 HTTP 服务 + 外部浏览器 | ~0 | 失去桌面应用形态，托盘/置顶/快捷键全废。否决 |

**选 A。** 代价是体积，收益是不引入 C 盘系统级依赖 + 渲染结果可控可复现。

### 4.2 架构（见上轮架构图）

```
Python 主进程（app/core 4441 行 + app/services，零改动）
   ↓ EventBus
UI Bridge（QObject，Slot/Signal）
   ↕ QWebChannel（双向 JSON）
Chromium 渲染层（app/web/，全新）
   ├── 主窗口视图    Home / Settings / Stats / About
   ├── 提示条浮层    透明 · 无边框 · 置顶 · 不抢焦点
   └── 位置编辑器    遮罩 + 拖拽预览
共用：tokens.css · 18 个 SVG 插画 · 站酷快乐体
```

**关键设计原则：**

1. **桥接面最小化**。只暴露一个 `Bridge` 对象，方法 ≤ 20 个：
   `get_snapshot()` / `save_settings(dict)` / `preview_sound(scheme)` / `pause(minutes)` / `resume()` / `rest_now()` / `open_position_editor()` / `save_position(x, y)` / `set_locale(code)` / `get_stats(range)`。
   事件侧只用**一个** `stateChanged(json)` 信号推快照。
   ⚠️ **不要把整个 EventBus 暴露给 JS**——会失控且无法测试。

2. **Python 端是唯一真相**。前端不做任何持久化，只做展示 + 意图上报。这样 `config.json` / `stats.json` 的读写逻辑、4441 行业务代码、8612 行业务测试**全部零改动**。

3. **tokens 单向生成**。写一个脚本从 `app/ui/theme/tokens.py` 生成 `tokens.css`，**禁止手写两份**。否则两边必然漂移，这会是长期维护的最大成本。

4. **提示条是独立透明 webview**。需要同时满足：
   ```python
   view.setWindowFlags(Qt.FramelessWindowHint | Qt.WindowStaysOnTopHint | Qt.WindowDoesNotAcceptFocus)
   view.setAttribute(Qt.WA_TranslucentBackground)
   view.page().setBackgroundColor(Qt.transparent)
   ```
   ⚠️ **这是整条路线最大的不确定点**。Chromium 合成在部分集显上有透明度闪烁/黑底风险。**失败时降级方案**：抓取窗口所在屏幕区域截图作为静态背景，再叠加内容（失去实时透明，但观感可接受）。

5. **资源加载**。`file://` + `setLocalContentCanAccessFileUrls(True)`，路径走现有 `get_resource_path('web')`（已适配 `_MEIPASS`）。或注册自定义 scheme `eyerest://` 更干净。

6. **字体与 DPI**。CSS `@font-face` 指向 `file:///.../assets/fonts/ZCOOLKuaiLe-Regular.ttf`；DPI 用 `setZoomFactor` 或 `--force-device-scale-factor`。

7. **位置编辑器坐标**。遮罩与拖拽在 HTML 内做，但**屏幕坐标换算与保存回 Python**，保证现有 `position_saved` API 与测试不变。

### 4.3 分阶段实施（可回滚，业务不动）

| 阶段 | 内容 | 通过条件 |
|---|---|---|
| **P0 可行性尖刺**（最先做） | 最小工程验证 4 件事：① 透明无边框 webview 能否稳定置顶且不抢焦点；② 中文在 Chromium 下的渲染与字体注入；③ 打包后 assets 能否被 `file://` 读到；④ 叠加后的体积与冷启动耗时 | **任一不过 → Web 路线直接否决，不要投入重写成本** |
| P1 桥接层 | `Bridge(QObject)` + 状态快照协议 + 纯 Python 单测（不需前端即可测） | Bridge 单测绿 |
| P2 主页 + 设计系统 CSS | tokens 生成脚本 + `tokens.css` + Home 页 | Home 与展示板并排比对 |
| P3 逐页迁移 | Settings → Statistics → About → VisualCue → PositionEditor | 每页单独比对验收 |
| P4 打包 | spec 加 `hiddenimports=['PySide6.QtWebEngineWidgets','PySide6.QtWebChannel']` + `collect_data_files`，**剔除 devtools pak 与多余 locale**，实测 sandbox / single-process 取舍 | dist 可运行且 C 盘零写入 |
| P5 测试策略 | 业务测试 8612 行全保留；UI 测试改为 ① Bridge 单测 ② 首启用 `runJavaScript` 断言关键 DOM id ③ 关键页截图留档 | 全套绿 |
| P6 回滚闸门 | 保留 Widgets 分支 tag；用环境变量 `EYEREST_UI=qt\|web` 两套并存，直到 Web 版稳定 | 可一键切回 |

### 4.4 Web 路线必须提前接受的风险

1. 体积 **144 MB → 约 355 MB**。
2. 内存 **+150 MB 左右**（Chromium 多进程）。
3. 冷启动可能 **+0.5~1.5 s**（Chromium 初始化）。
4. QtWebEngine 在 PyInstaller onedir 下打包坑多：resources、locales、`qtwebengine_locales` 缺一个就白屏或崩溃。
5. **透明 + 置顶 + 无焦点三者同时满足在 WebEngine 上比在 Widgets 上更难**，直接决定路线成立与否。
6. 长期维护变成"前端 + Python"两套技术栈，调试链更长（DevTools 可用是优点）。
7. 失去 Qt 原生控件的可访问性与输入法一致性；托盘、全局快捷键、开机自启体系需重新接线。

## 5. 建议路径

分两步，先花最小成本把最刺眼的一项解决掉，再决定是否换引擎。

**第一步（现引擎内就能做，投入小、收益大）**
1. 把展示板原图存入仓库 `docs/design/`，**取色器锁定权威色值**（不要照抄方案文本的 `#4CAF8A`）。
2. **VisualCue 运行时皮肤暖色化**——这是最后一个还在用旧 emoji 皮肤的用户可见界面，也是方案明确点名的一项。
3. **Hero 补植物背景 + 右上角四行节奏总览**（方案 1.4 的新增项）。
4. 主插画换柔光质感资产（ImageGen 位图或 SVG 叠模糊层）。

**第二步（同时进行，只做尖刺）**
一件事：验证 WebEngine 的透明置顶提示条。

- 通过 → 值得投入 P1~P6。
- 不通过 → 走 **Qt Quick**（92%、+30 MB），或接受 Widgets 的 80% 上限。

**最后一句必须说的**：把目标从"1:1"换成"逐区块对齐 + 可验收清单"。否则无论换哪条引擎，都会继续不满意——因为问题不在引擎，在目标函数没有终点。

## 9. P0 尖刺：执行清单

**唯一目标**：回答一个问题——「透明 + 无边框 + Always on Top + No Focus 的小型 VisualCue，在 QtWebEngine 下能否稳定工作，且不干扰桌面其它窗口。」

**最小实验体**：一个 400×120 的 `QWebEngineView`，`WA_TranslucentBackground` + `FramelessWindowHint | WindowStaysOnTopHint | WindowDoesNotAcceptFocus`，内容为暖色圆角卡片 + 一行文字 + 1 个 CSS 呼吸动画。**不含任何 EyeRest 业务逻辑。**

**必测场景（任一失败即否决 Web 路线）**：

| 类别 | 场景 |
|---|---|
| 系统 | Windows 10、Windows 11 各一次 |
| 缩放 | 100% / 125% / 150% DPI |
| 多显示器 | 主副屏分别放置、跨屏拖动、副屏为主显示器 |
| 焦点 | 弹出时当前应用仍可继续输入（键盘 + 鼠标均不丢焦点） |
| 窗口切换 | Alt+Tab 后提示条仍在最上层，且不进入切换列表 |
| 全屏应用 | 全屏视频 / 全屏游戏下的表现（是否被压制、是否闪黑） |
| 系统事件 | 锁屏→唤醒、显示器休眠→唤醒后是否正常 |
| 渲染 | 透明区域无黑底、无闪烁；连续显示 3 小时无内存泄漏 |
| 性能 | 常驻内存与 CPU 占用（以 Widgets 版为基线对比） |

**判定与出口**：

- **全部通过** → 进入 Web 原型阶段，与 QML 横向比较最终投入产出。
- **任一失败** → 记录失败场景与复现条件，**路线切至 Qt Quick**，不再投入 Web 重写成本。

## 10. 多状态视觉验收矩阵

**不要只拿展示板截图做验收。** 展示板只画"最美状态"，直接照它验收必然出现"中文截图漂亮、一换英文整个布局崩掉"。

每个页面必须在以下真实状态下比对：

| 状态 | 说明 |
|---|---|
| 正常 | 有数据、运行中 |
| 暂停 | 托盘暂停 30min / 2h / 今天 |
| 空数据 | 首次启动、无统计记录、显示 `--` |
| 长文本 | 最长状态文案、最长位置名 |
| 英文 | 全量切 en，验证长度膨胀（约 1.6×）不破版 |
| 125% DPI | 布局不重叠、不裁切 |
| 静默模式 | 游戏 / 会议模式下的 UI 表现 |

**页面 × 状态清单**：

| 页面 | 尺寸 | 需覆盖状态 |
|---|---|---|
| Home | 900×680 | 正常 / 暂停 / 空数据 / 长文本 / 英文 / 125% |
| Settings | 900×680 | 正常 / 未修改（隐藏保存提示）/ 已修改 / 保存成功 / 英文 / 125% |
| Statistics | 900×680 | 空数据 / 单日 / 多日 / 英文 |
| VisualCue | 400×120 | 四类提示 × 三 Skin × 三强度 / 英文 |
| PositionEditor | 全屏遮罩 | 六种预设位置 / custom / 拖动中 / 英文 |
| BreakWindow | 全屏 | 正常 / 倒计时 / 跳过 / 英文 |

**判定**：截图并排留档在 `docs/design/acceptance/`（命名 `页面-状态[-备注].png`），逐条勾选。**"中文漂亮、英文崩版"这类问题必须在同一轮修掉，不得延后。**
